## 一、结论

静态归属链通过。MGR 与 Watcher 的模型类型都位于各自的模组程序集，未发现类型级归属分裂。

P0 未关闭。静态审计已完成；两个版本的运行时归属见 [020-E](020-E-P0运行时归属与缓存.md)。连续两局缓存仍未完成。

关键结论：

- MGR 通过根加载器加载 `lib/0.113.0/MGRMod.dll` 或 `lib/0.111.0/MGRMod.dll`，并把 payload 程序集关联到 `MGRMod`。
- Watcher 直接由游戏加载 `Watcher.dll`，`Mod.assemblies` 会包含该程序集。
- MGR 与 Watcher 都未注册自定义事件、遭遇、怪物、章节或先古。
- `SourceCache` 的静态缺陷已确认：只比较源数组引用，没有策略版本。运行时串缓存尚未复现。
- Watcher 0.10.20 的 `min_game_version` 是 `0.113.0`，不能在 0.111.1 加载。

## 三、归属链

### 3.1 Watcher

Watcher 没有二级加载器。游戏 `ModManager.TryLoadMod` 读取 `Watcher.dll`，初始化后把程序集加入 `Mod.assemblies`。`AssemblyInfo.Init` 再以 `Mod.assemblies` 建立 `Assembly → Mod` 映射。

链路：

```text
Watcher.json (id=Watcher)
  → Watcher.dll
  → Mod.assemblies
  → AssemblyInfo.ModMap
  → ContentOwnership.GetOwnerModId(type)
  → Watcher
```

`AssemblyInfo.Init` 在 `ModManager.Initialize` 之后执行。证据：

- `MegaCrit.Sts2.Core.Modding/ModManager.cs:796-805`：加载 `modId + ".dll"`。
- `MegaCrit.Sts2.Core.Modding/ModManager.cs:885-888`：加入 `mod.assemblies`。
- `MegaCrit.Sts2.Core.Helpers/OneTimeInitialization.cs:80`：`AssemblyInfo.Init()`。
- `MegaCrit.Sts2.Core.Modding/AssemblyInfo.cs:21-34`：按 `mod.assemblies` 建映射。

### 3.2 MGR

MGR 根程序集只包含 `MGRMod.Loader.Bootstrap`。初始化过程：

```text
MGRMod.json (id=MGRMod)
  → MGRMod.dll (loader)
  → Bootstrap.Initialize
  → 选择 lib/0.113.0/MGRMod.dll 或 lib/0.111.0/MGRMod.dll
  → 校验 SHA-256
  → 加载 payload
  → AssociateAssemblyWithMod(payload)
  → payload MGRMod.Entry.Initialize
```

0.113.1 中存在 `ModManager.AssociateAssemblyWithMod(string, Assembly)`。加载器调用该方法，把 payload 加入 `MGRMod.assemblies`；`AssemblyInfo.Init` 随后建立映射。

0.111.1 中没有 `AssociateAssemblyWithMod` 方法。加载器回退到 `Mod.assemblies` 字段，把 payload 加入列表。0.111.1 的 `Mod` 类同样有该字段。

已有 0.2.0 无头日志记录了 MGR payload 关联：

```text
[INFO] Associated assembly MGRMod, Version=1.0.0.0, ... with mod MGRMod
```

日志路径：`TMP/0.2.0/gui-test.stdout:519`。该日志同时显示角色模组隔离先加载、MGR 后加载，而自动识别直到主菜单就绪后才执行。证据：同文件 `:289`、`:290`、`:1675-1676`。

### 3.3 本地归属缓存的建立时机

`ContentOwnership.EnsureBuilt` 只在首次读取归属时构建一次，之后不会重建。证据：`9.SRC/src/Runtime/ContentOwnership.cs:119-164`。

角色模组隔离的 `Plugin.Initialize` 不调用 `ContentOwnership`；自动识别发生在主菜单就绪事件。证据：`9.SRC/src/Plugin.cs:14-71`。

因此在当前加载顺序下，MGR payload 与 Watcher 程序集已经加入 `Mod.assemblies`，之后才建立本地归属缓存。未发现「缓存早于 MGR 关联」的路径。

限制：该结论是静态顺序分析。运行时仍需记录 `GetOwnerModId(typeof(MgrCharacter))` 与 `GetOwnerModId(typeof(Watcher))`。

## 四、内容分类

统计依据是当前 DLL 的反编译结果与属性：

- MGR 的 `[RegisterCard]` 94 个，`[RegisterRelic]` 12 个，`[RegisterPotion]` 3 个，`[RegisterCharacter]` 1 个。
- MGR 的起始牌属性为 4 张 `MgrStrike`、4 张 `MgrDefend`、1 张 `LittleParade`、1 张 `Lullaby`；起始遗物为 `MyFriend`。
- Watcher 的 `StartingDeck` 为 10 张卡，`StartingRelics` 为 `PureWater`。
- 两侧都没有 `EventModel`、`EncounterModel`、`MonsterModel`、`ActModel` 或 `AncientEventModel` 子类。

Watcher 共有 94 个具体卡牌类型。83 个在 `WatcherCardPool`，8 个在 `WatcherDerivativeTokens`；其余是特殊或辅助卡牌子类。全部位于 `Watcher.dll`，没有动态程序集。

MGR 的 `MgrNoteCardFactory` 只通过 `CreateCard` 创建已有类型，没有 `TypeBuilder`、`AssemblyBuilder` 或动态代理。证据：`TMP/0.3.0/P0-decompiled/MGRMod/MGRMod.Mechanics/MgrNoteCardFactory.cs`。

## 五、其他角色模组的可识别类别

当前已安装的两个角色模组是 MGR 与 Watcher。摄政是游戏原版角色，不属于模组内容。

已有 0.2.0 自动识别日志只列出 MGR：

```text
[auto] built. mods=39 character=1
[auto] character=MGRMod kind=Character reason=已注册角色
```

证据：`TMP/0.2.0/gui-test.stdout:1675-1676`。该次测试中 Watcher 被禁用。

按当前版本静态分类：

| 当前角色 | 其他角色模组 | 其他模组内容类别 |
|---|---|---|
| MGR | Watcher | 角色、94 张卡、10 张遗物、3 张药水；无事件、遭遇、章节、先古 |
| Watcher | MGR | 角色、94 张卡、12 张遗物、3 张药水；无事件、遭遇、章节、先古 |

因此当前安装集下，需要隔离的可识别类别是角色、卡牌、遗物与药水。事件、遭遇、怪物、章节、先古当前没有 MGR 或 Watcher 内容，但过滤代码仍应保留这些分类，供其他角色模组使用。

## 六、边界风险

以下问题不是类型级归属分裂，但会影响「其他模组内容不得进入本局」的目标。

### 6.1 直接读取 `ModelDb.AllCharacters`

`ModelDb.AllCharacters` 是原版 6 角色数组。Watcher 的 `ModelDbAllCharactersPatch` 用后置补丁追加 Watcher。证据：

- `4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Models/ModelDb.cs:146-155`
- `TMP/0.3.0/P0-decompiled/Watcher/WatcherMod/ModelDbAllCharactersPatch.cs:8-20`

当前本模组只在 Orobas 作用域内过滤 `AllCharacters`。`9.SRC/src/Patches/SpecialPatches.cs:8-39` 的 `_depth` 只由 `OrobasPrefix` 增加。

因此 MGR 局中，Orobas 之外直接读取 `ModelDb.AllCharacters` 的代码仍可能看到 Watcher。P2 必须覆盖该路径；不能把「角色列表已过滤」当作全局保证。

### 6.2 直接读取 `UnlockState.CharacterCardPools`

`MgrOrobasCardPoolScopePatch` 与 `MgrScopedCharacterCardPoolsPatch` 只排除 MGR：

- `.../MGRMod.Patches/MgrScopedCharacterCardPoolsPatch.cs` 仅过滤 `pool is MgrCardPool`。
- `.../MGRMod.Patches/MgrCrossCharacterCombatCardPoolPatch.cs` 仅在当前角色不是 MGR 时排除 MGR。

MGR 局中，这两条路径不会排除 Watcher。若 Orobas、Kaleidoscope、Splash 或其他生成器直接读取 `UnlockState.CharacterCardPools`，可能绕过卡池级过滤。计划 P2 已列出 Orobas 与 Kaleidoscope；本审计补充 `CardFactory.GetDistinctForCombat`、`GetForCombat` 与 `UnlockState.CharacterCardPools` 的直接读取。

### 6.3 Watcher 的 Darv 遗物注入

`WatcherDarvRelicPatch` 向 `Darv` 的全局有效遗物集加入 `VioletLotus`，集合的谓词是 `owner.Character is Watcher`。证据：`.../WatcherMod/WatcherDarvRelicPatch.cs:64-103`。

静态看，Darv 在 MGR 局不会选择该集合。未发现 MGR 局通过此路径直接获得 Watcher 遗物。

`Darv.AllPossibleOptions` 仍会枚举全局集合；这属于图鉴或事件可能选项，不是当前本局内容池。P2 验收时只检查本局实际选项即可，除非后续把图鉴纳入范围。

### 6.4 `HolyWater` 事件遗物

Watcher 通过 `ModHelper.AddModelToPool<EventRelicPool, HolyWater>()` 把 `HolyWater` 加入事件遗物池。证据：`.../WatcherMod/WatcherBootstrap.cs` 与 `.../WatcherMod/HolyWater.cs`。

本模组的动态遗物池补丁会扫描 `RelicPoolModel` 子类并覆盖 `GetUnlockedRelics(UnlockState)`。当前未验证 `EventRelicPool` 是否实际命中该补丁。P2 必须用 MGR 局检查 `EventRelicPool`。

### 6.5 MGR 的诅咒与状态生成

MGR 的 `MgrNoteCardFactory` 与 `MgrCurseUtils` 直接读取 `StatusCardPool.AllCards` 或 `CurseCardPool.AllCards`。证据：

- `.../MGRMod.Mechanics/MgrNoteCardFactory.cs:56-63`
- `.../MGRMod.Mechanics/MgrCurseUtils.cs:60-73`

当前 Watcher 没有注册诅咒或状态卡，因此 MGR/Watcher 两者之间未发现此路径的泄漏。未来加入其他带诅咒或状态卡的角色模组时，该路径需要纳入测试。

## 七、`SourceCache` 审计

### 7.1 代码事实

`9.SRC/src/Patches/PoolPatches.cs:8-37` 的缓存只有两个字段：

```text
Source
Filtered
```

缓存键是 `CardPoolModel` 实例。是否重建只看：

```text
ReferenceEquals(cache.Source, source)
```

没有策略版本、隔离集、保护集或设置版本。

游戏侧 `CardPoolModel.AllCards` 把生成结果存入 `_allCards` 字段并复用同一数组。证据：`4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Models/CardPoolModel.cs:14-52`。

因此同一 `CardPoolModel` 实例在两次运行中拿到同一个源数组时，过滤结果不会重建。

### 7.2 运行时影响

0.2.0 中，模组角色局直接令 `RunContext` 停用过滤。此时 `FilterPolicy.CardsActive` 为 false，`SourceCache` 不参与读取，所以 0.2.0 没有显示出串缓存。

0.3.0 的 P1 会让当前角色模组局启用过滤。若保留现有缓存实现：

1. 原版角色局建立 `Source → Filtered`，移除角色模组卡。
2. 切换到 MGR 局，隔离集变为「Watcher」。
3. 同一个 `MgrCardPool` 或 `WatcherCardPool` 的源数组引用不变。
4. `SourceCache` 继续返回原版局的过滤结果，当前角色模组内容可能被误删。

这是静态可证的风险。未执行连续两局运行时复现。

### 7.3 其他缓存

- `CardPoolModel.AllCardIds` 独立缓存 `_allCardIds`，由 `AllCards` 生成。证据：`CardPoolModel.cs:60`。若它在过滤前建立，会保留角色模组 ID。
- `ModelDb.AllCards` 在 `Preload` 中物化。证据：`ModelDb.cs:115`、`:508-525`。它不是本功能的运行期唯一出口，但可能污染图鉴、统计或直接读取方。
- `ModelDb.AllCharacterCardPools`、`AllCharacterRelicPools`、`AllCharacterPotionPools` 也按 `AllCharacters` 缓存。P2 需要检查它们是否被运行路径读取。

### 7.4 失效方案

P3 计划已具备可验证方案：

- 给 `SourceCache` 增加 `PolicyVersion`。
- 策略版本由 `RunContext` 的运行状态、保护集、隔离集、模式与设置版本组成。
- `SourceCache` 比较 `Source` 引用和 `PolicyVersion`；任一不同则重建。
- 运行结束、设置变化与策略切换时递增版本。
- 对 `AllCardIds` 和 `ModelDb.AllCards` 单独测试是否需要清理。

该方案可验证，但尚未实现。P0 的「缓存残留可复现」门槛仍未满足。
